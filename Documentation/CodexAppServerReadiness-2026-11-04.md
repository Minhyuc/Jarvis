# Codex App Server 연결 준비 점검

점검일: 2026-11-04 (Asia/Seoul). 운영 코드·권한·실행 설정은 변경하지 않았다.

후속 구현: 아래 내용은 구현 전 점검 기록이다. 이후 같은 날짜에 CLI를 유지한 App Server 텍스트 연결 모드를 추가했다. 현재 사용법과 실제 두 턴 세션 검증 범위는 [연결 안내](../Tools/CodexLocal/README.md)의 App Server 절을 참고한다. 파일·수정·셸 기능은 아직 활성화하지 않았다.

## 결론

현재 Mac에서 App Server의 기본 기동과 JSON-RPC 초기화는 가능하다. JARVIS 모델의 가중치나 한국어 명령 이해도를 바꾸는 것이 전제 조건은 아니다. 그러나 현재 JARVIS 연결은 App Server 클라이언트가 아니므로, 파일 수정 도구를 단순히 활성화해서 사용 가능한 상태는 아니다.

## 실제 확인한 범위

- 설치된 실행 파일: ChatGPT 앱에 포함된 `codex-cli 0.165.0-alpha.1.2`.
- 기존 CLI의 ChatGPT 로그인 상태 확인: 성공. 로그인 토큰·계정 원문은 출력하지 않았다.
- 별도의 임시 CODEX_HOME과 임시 작업 디렉터리에서 `codex app-server --stdio --strict-config` 실행: 성공.
- JARVIS 기존 차단 기능 목록을 유지한 상태에서 `initialize` 요청 및 `initialized` 통지: 성공.
- 같은 연결의 `model/list`: 성공, 목록 9개 응답. 이 목록은 현재 계정의 모든 모델 사용 권한을 검증한 결과가 아니다.
- 계정 로그인 정보 복사, 사용자 프로젝트 연결, `thread/start`, `turn/start`, 파일·명령 RPC는 수행하지 않았다. 테스트 프로세스는 종료했다.
- 이 초기화 검증은 App Server에서 기존 로그인 재사용, 모델 추론, 파일 수정·빌드가 성공한다는 검증을 대신하지 않는다.

## 특히 주의할 실제 구조 차이

1. **승인 통지가 모든 작업의 사전 검토를 보장하지 않는다.** 공식 문서는 설정에 따라 명령·파일 변경이 승인을 요구할 수 있다고 설명한다. workspace-write에서 자동 허용되는 변경을 JARVIS가 반드시 적용 전에 검토한다고 가정하면 안 된다. 제한된 도구 중계 또는 작업 사본에서 수정 후 원본 반영을 별도로 승인하는 등 명확한 실행 구조를 선택하고 검증해야 한다.
2. **샌드박스는 해제할 필요가 없다.** Mac 앱은 샌드박스를 유지하고, 외부 보조 서비스는 선택한 프로젝트·작업 범위만 처리하도록 별도 제한해야 한다. 앱의 폴더 선택 권한이 외부 프로세스에 동일하게 전달된다고 가정하지 않는다.
3. **임의 RPC 프록시는 만들지 않는다.** App Server에는 계정·설정·파일·프로세스를 제어하는 API도 있다. JARVIS에서 필요한 메서드만 노출하고, 샌드박스 밖에서 실행되는 `thread/shellCommand`·`process/spawn` 같은 경로를 일반 작업 경로로 사용하지 않는다.
4. **사용자 설정과 인증을 분리해서 검증한다.** 이번 임시 환경 테스트는 개인 설정·플러그인·훅의 유입을 피하기 위해 기존 인증 저장소를 사용하지 않았다. 실제 연결에서는 Codex의 관리 인증을 사용하며 토큰을 직접 복사하지 않고, 불필요한 자동 도구·설정 유입도 차단해야 한다.
5. **설치 버전은 alpha다.** 최신 문서의 모든 필드가 이 실행 파일에 있다고 가정하지 않는다. 설치 버전이 생성한 스키마와 실제 응답을 기준으로 구현하고, 업그레이드 시 호환성 검사·실패 시 차단을 유지한다.

## 권장 구현 순서와 완료 기준

1. 기존 텍스트 연결을 보존한 채 전용 App Server 어댑터를 추가한다. 초기화·계정 확인·모델 목록·텍스트 turn·세션 재개·중단·재연결을 먼저 검증한다.
2. 프로젝트 선택과 읽기 전용 분석을 연결한다. 범위 밖 경로, 심볼릭 링크 우회, 권한 회수와 안전 잠금을 테스트한다.
3. 작업 사본의 변경 검토와 승인 후 원본 반영을 구현한다. 기존 사용자 수정·동시 변경·취소·부분 실패·복구를 검증한다.
4. 빌드·테스트 실행을 추가한다. 실행 명령·작업 디렉터리·권한과 제한 시간을 검증하고, 명령 종료 성공과 실제 기능 검증 성공을 구분한다.
5. 수동 연결이 안정된 뒤 앱이 보조 서비스의 시작·종료·버전을 관리하게 한다. 터미널 없는 수명 관리는 App Server 연결과 별도 개발 항목이다.

각 단계에서 허용·차단·승인·거절·취소·긴급 잠금·재연결 중복 방지 테스트를 통과한 범위만 활성화한다. 모델이 승인 여부를 결정하거나 정책을 수정하게 하지 않는다.
